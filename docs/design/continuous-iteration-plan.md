# Awake_DW · 持续迭代计划（2026-11-17 建立）

> 定位：这是**操作层**的长期计划。`roadmap.md` 记录版本时间线与已完成范围；本文件回答「下一版做什么、多久做一次、什么算完成、停滞后怎么恢复」。
> 约束不变：`rules.md`、`AGENTS.md`、`visual-baseline.md` 仍是硬边界；本文件不新增功能承诺，只管理节奏与取舍。
> 一句话：**每 1–2 周一个可回退的小版本；每版都有自动化证据与一组真机走查项；不追求功能数量，追求完成度。**

## 1. 为什么需要它

- 2026-10-23 发布 2.9.0 后，项目停滞约三周。不是因为没有想法，而是因为：
  1. 版本之间只有「版本计划」，没有**滚动待办**——做完一版就不知道下一版是什么；
  2. 验收依赖使用者集中走查，一旦没空，整条线停住；
  3. 细节优化越做越细，缺少「下一件值得做的事」的排序规则。
- 本计划把「迭代」变成默认状态：即使使用者一段时间不在，也能按队列继续做**不依赖确认**的工程/体验项，并把待确认项集中到一次走查里。

## 2. 节奏

| 周期 | 动作 | 产出 |
| --- | --- | --- |
| 每 1–2 周 | 一个候选版本（1 个主变量 + 最多 1 个配套改动） | 代码、测试、截图、plan、QA 草稿 |
| 每 2 周 | 一次 10 分钟真机走查卡（3–5 项） | 通过 / 问题 / 偏好三项回传 |
| 每 4 版 | 一个「保养版」：性能、无障碍、测试、构建、docs、dist 治理 | 不带新观感的稳定性版本 |
| 按需 | 使用者确认方向后，才排结构级大版本 | 方向稿 + 真机闸门 |

- **发布**：代码门禁全绿 + 真机走查通过（或使用者明确要求「先发再验」并如实披露）才提升版本号。
- **未验收不阻塞**：连续两个候选没有真机回传时，下一版改做不依赖验收的保养项；第四个候选前必须安排一次走查或明确「先发后验」。
- **不使用 alpha/beta/RC 后缀**（rules §八.5）；未发布候选在文档里写「候选」，不写进 versionName。

## 3. 选下一件事的排序

1. **P0 回归/阻断**：闪退、数据错误、构建失败、主操作不可达。
2. **P1 用户可感知的完成度**：首屏、核心记录回路、纠错路径、反馈节奏、设置可读性。
3. **P1 工程健康**：视觉基线、无障碍、性能、测试覆盖、构建时间、发布卫生。
4. **P2 内容与氛围**：主题、素材、文案、粒子/场景（需确认素材方向）。
5. **P3 新能力**：新页面、新主题、统计扩展等——默认不做，先提案确认（已否决方向见 §8）。

补充规则：
- 一版只回答一个「使用者能感到什么」；不把重构、视觉、业务混进同一个版本。
- 连续两版都是「纯参数微调」时，第三版必须换成识别级变化或保养版。
- 任何新装饰先回答「放在哪里、为何存在、如何不打扰」；答不出就不做。

## 4. 每版固定流程

1. **读**：`rules.md`、`AGENTS.md`、`visual-baseline.md`、`roadmap.md`、本文件、对应 plan。
2. **写**：日期化 plan（范围、非目标、设计决定、验收条件、回退方案）；设计变更先取得确认。
3. **做**：小步提交；domain 行为先写测试；视觉改动走基线；新增共享能力遵守「第二处使用即下沉」。
4. **验**：`./gradlew ktlintCheck build` 全绿；`git diff --check`；相关视觉基线 `AWAKE_VISUAL_BASELINE=check` 逐模块通过；真机走查项单列。
5. **记**：更新 CHANGELOG、QA、roadmap 的版本状态；未完成项如实披露，不宣称已验收。
6. **发**（仅在确认后）：提升 versionCode/versionName、生成 Release APK 与 SHA-256、dist 治理、提交/打 tag。

## 5. 质量门禁（Definition of Done）

| 维度 | 门禁 |
| --- | --- |
| 构建 | `ktlintCheck build` 全绿；无新增 TODO/FIXME/注释死代码 |
| 行为 | domain 用例覆盖；data 层按风险补；测试名用业务语言 |
| 视觉 | 统计/设置基线 `check` 通过；首页像素基线环境解开后补入；改变观感必须有前后对照 |
| 触控 | 可点目标 ≥ 48dp；自绘控件显式 `ControlMinHeight` |
| 大字 | 360dp × 1.3× 可用；1.5×/2× 允许滚动但不截断、不覆盖 |
| 动效 | 正常/减少动态两套路径；装饰只进 draw 相；不逐帧分配 |
| 无障碍 | 语义等价、TalkBack 可读、长按类隐藏手势有可见说明 |
| 内容 | 文案库长度/唯一性/不含竖线/无第二人称；引文零文言、出处完整 |
| 发布 | 版本、APK、SHA、QA、CHANGELOG、dist 同步 |

## 7. 验收闭环（让使用者 10 分钟就能回传）

每版 QA 末尾固定给出一张「走查卡」，最多 5 项，每项写清：
1. **页面/入口**（从哪进）；
2. **操作**（点什么、拖什么）；
3. **预期**（看到什么/听到什么）；
4. **证据**（截图/录屏路径，或自动化已覆盖的部分）；
5. **未通过时**（需要记录的现象：主题、字号、机型）。

回传只需三类：**通过 / 有问题（附现象）/ 偏好（喜欢/不喜欢）**。没有回传时，按 §2 继续保养项，不把「未回传」当成通过。

## 8. 反停滞与反反复

- **停滞检测**：若超过 14 天没有提交，执行「恢复清单」：
  1. `git status` + `ktlintCheck build` 确认仓库健康；
  2. 跑设置/统计基线 `check`，看是否有环境漂移；
  3. 从滚动待办取一个**不依赖确认**的最小项（保养版优先）；
  4. 更新 roadmap/QA，再决定是否排新方向。
- **防反复**：已否决方向不再重开，除非使用者明确要求并给出新理由：
  - 环体液化（1.8.0 否决）；
  - 信纸方向 1.1–1.3（1.3.1 回退）；
  - 年度信纸（2.3.0 引入，2.5.0 撤除）；
  - 桌面小部件（2.2.0 使用者否决）；
  - Bento 卡片、AI/云同步、连胜/社交、玻璃拟态/高斯模糊（研究稿 §6）。
- **防过度**：新装饰不引入网络资源、3D、模糊滤镜；不为视觉提示新增持久化键；不借优化改业务、导航、权限。

## 9. 版本号与发布

- `x.y.0`：一个用户可感知的小版本；`x.y.z`：修复；`x.0.0`：结构/视觉方向级变化。
- 发布物：Release APK + SHA-256 + QA + CHANGELOG；`dist/` 只保留最新版与使用者指定的里程碑。
- 提交按「文档 / 实现 / 发布」拆分；仅在使用者要求时提交/推送，不擅自强推。

## 10. 使用方式

- **开始一轮**：打开本文件 §6，选下一项；若该项需要确认，先问；不需要确认就直接写 plan。
- **结束一轮**：更新 §6 状态、QA、CHANGELOG、roadmap；在回复里给出「这轮改变了什么 / 证据 / 待验收 / 下一件」。
- **迷路时**：回到 §3 排序，不凭手感加功能；先问「这让使用者的体验更优雅、更自然、更不打扰吗」。
