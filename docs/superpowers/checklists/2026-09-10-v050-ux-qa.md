### Fixed after re-reading the notification path: the receipt carried a greeting

The notification action is the busiest logging path for a reminder app — the user taps 「记一杯」 without opening the app — so its receipt was audited last, and it was wrong. `loggedAck()` set its title from `titleOf(currentSlot())`, i.e. the time-of-day greeting, so tapping the action turned the notification into 「午安 ☀ / 已记一杯」. That reads as *another reminder arriving* and drowns out the confirmation. Same class of defect as the home screen's shared praise/cat line: two channels sharing one slot. Now the receipt states what happened (「已记一杯」) and its body carries the day's progress (「今天共 750ml」), or 「今日份水灵达成 ✨」 when that cup reached the goal — the notification shade is the only place that can tell the user, since they are not looking at the in-app ribbon.

Supporting this, `LogResult.Logged` now exposes `totalAfterLog`. The use case already computed that value to decide `celebrated` and then discarded it; the notification caller has no access to the ring, so the receipt had nothing to report. `RecordingBroadcast` reads it through an exhaustive `when`, so a future variant fails compilation rather than throwing `CastException` in a receiver.

Why it survived this long: the existing test asserted only `EXTRA_TEXT`, never `EXTRA_TITLE`. The title assertion is now in place, and the receipt title is checked against every slot's greeting.

- [x] `:core:domain` `LogWaterUseCaseTest`: `totalAfterLog` tracks the running total, matches the repository's own tally, and survives custom amounts.
- [x] `:core:notification` `ReminderReceiverRobolectricTest`: the receipt's title is not any slot greeting and its body carries the total; the goal-reaching scenario asserts the receipt switches to the goal line.

### Toolchain flake: Robolectric's download lock on Windows

Two consecutive full builds failed with `IllegalStateException: Couldn't create lock file C:\Users\zhuyurui\.robolectric-download-lock`, from Robolectric's `MavenDependencyResolver.whileLocked`, once in `:feature:stats` and once in `:core:sound` — unrelated modules, and neither failure was a real test failure. It is contention on a single lock file in the user home when several Robolectric JVMs run in parallel.

Workaround, confirmed: pre-create the file once (`touch ~/.robolectric-download-lock`, or any empty file). `whileLocked` calls `createNewFile()`, which succeeds trivially when the file is already there and fails intermittently when it has to create it. The file is left in place for now. If this keeps recurring, the durable fix is to add a `doFirst` that touches the lock before Robolectric test tasks, or to run Robolectric offline against a pre-populated dependency directory — deliberately not done here, because it changes the user's build configuration for what may be a machine-specific av/permission quirk.

### Touch-target audit (added 2026-09-10, after the copy/feedback rounds)

The baseline has said "touch targets stay at or above 48dp" for a while, but **nothing enforced it** for hand-rolled controls. `Modifier.clickable` and `combinedClickable` do not carry Material3's automatic minimum interactive size — unlike `Button`, their height is entirely whatever the padding happens to produce. Sweeping every hand-rolled click target in the app turned up four real violations:

- [x] `OnboardingScreen` 「以后再说」— `labelLarge` plus 10dp vertical padding ≈ **40dp**. Fixed with `ControlMinHeight` + vertical centring; the visual padding is unchanged so the text still sits where it did.
- [x] `CopyEditorSheet` 「＋ 新增一句」— `labelMedium` plus 10dp vertical padding ≈ **36dp**, the worst of the four. Fixed.
- [x] `CopyEditorSheet` copy rows — an explicit `heightIn(min = 44.dp)`, i.e. 44dp, just under the line. Raised.
- [x] `BadgesRow` fact columns — **no minimum at all**; two lines of text naturally came to ≈40dp. This one matters most because the middle column is the long-press revert target, so an undersized target means a long press that misses.

Also collapsed the scattered `48.dp` literals at the remaining hand-rolled targets onto the shared `ControlMinHeight` constant, so the rule now lives in one place instead of six. Compliant by inspection and left alone: `AwakeConfirmDialog` actions (48dp), `LogButton` (56dp), quick-sip chips (48dp), settings controls (48–86dp), timeline rows (48dp), the cat hint chip (48dp), and `CatFigure` (84dp, and it already exposes `role = Button` plus an `onClick` semantic action, so it is reachable by TalkBack).

- [x] `:feature:onboarding` gained compose test dependencies and a test manifest — it previously had no compose test source set at all, which is why this screen had never been measured. `OnboardingLayoutTest` now covers both buttons' heights and asserts that 「以后再说」 genuinely completes the page (the only exit for someone who does not want the guide).
- [x] `CopyEditorTouchTargetTest` measures 恢复默认 / group header / 「＋ 新增一句」 / a copy row against `ControlMinHeight`.
- [x] `BadgesRowLayoutTest` gains a height check for all three fact columns, alongside its existing equal-width checks.

### Testing gotcha worth remembering (1): clicking does not scroll for you

`performClick()` does **not** scroll the target into view. After `performScrollTo()` on a neighbouring node, a header can sit just outside the viewport and the click silently misses, which reads as "the interaction is broken" rather than "the test scrolled wrong". Always `performScrollTo().performClick()` when the target follows another scrolled element. Long-press has the same constraint, and the helper needs an explicit `androidx.compose.ui.test.longClick` import. Likewise, `performScrollTo()` only pulls a node to the edge of the viewport — if it has to *appear in a screenshot*, scroll to that node itself before capturing.

### Testing gotcha worth remembering (2): screens with infinite animations hang the test

Both new compose tests initially hung rather than failed, which costs far more time than a normal red test. Two different remedies are needed, and which one depends on what drives the animation:

- **Onboarding** — the droplet breath is a `rememberInfiniteTransition` driven by the compose clock, so `waitForIdle()` never returns under `autoAdvance`. Fix: `mainClock.autoAdvance = false` and drive frames with `advanceTimeBy`, never calling `waitForIdle`. Same approach as `HomeVisualReviewTest`. The first run of this test wedged a Gradle daemon and had to be killed with `./gradlew --stop`.
- **Settings / stats** — their particle backdrops are governed by the system animator scale, so the existing tests there zero `Settings.Global.ANIMATOR_DURATION_SCALE` instead and keep using `waitForIdle` freely. `SettingsVisualReviewTest` already did this; the new touch-target test had to adopt it.

Practical rule for this repo: any new compose test on a screen that has particles has to pick one of those two switches up front. A hang here is not a slow test, it is an unbounded one.

### Known limitation: the confirm dialog cannot be photographed here

`AwakeConfirmDialog` renders in a separate window, so drawing the activity root misses it. `captureToImage()` on the dialog node refuses outright below API 28 (`Cannot currently capture dialogs on API lower than 28!`), and raising the test to SDK 28 only moves the failure to a `ComposeTimeoutException` inside `forceRedraw` — Robolectric never delivers the redraw that path waits for. Two attempts were enough to call it: dialog *capture* is not achievable in this harness.

Consequence, stated plainly: the dialog's appearance (card padding, action spacing, contrast on dark themes) has **no** automated evidence. Its behaviour is covered by the revert-chain test above, and its layout is a straight port of the previously shipped copy-editor dialog plus ≥48dp action targets. Dialog appearance is therefore promoted to a required device-QA item rather than something claimed as verified.

### Cross-component effect found while auditing shared components

`RingCenterContent` is shared between the home screen and the splash's seed preview (`HomeSeedPreview` renders it with `centerNote` absent and `reduceMotion = true`). The seed preview is behaviourally unchanged: the added parameter defaults to null so it still reads `今日已喝`, and the new crossfade takes a 0 ms duration under reduced motion. No capture exists for the splash, and the seed preview is private, so this rests on that reasoning plus the home-screen captures rather than on its own evidence.

The real find was indirect: `SplashMorph` estimates the home ring centre with `GREETING_TEXT_HEIGHT_SP = 44.sp`, which assumes a **single-line** greeting, and its comment used to say that folding to two lines costs about one line height of residual deviation because the greeting was capped at `maxLines = 2`. Removing that cap (baseline §3: do not truncate) means over-long user greetings can now fold to three or more lines and widen that deviation further. Impact is bounded: the built-in 108 lines are 11–18 characters, so in practice the deviation stays at the already-tolerated one line, and only hand-written greetings beyond roughly 32 characters push it past two. The trade-off is now recorded in both the baseline and the stale comment was corrected so the code no longer claims a cap that does not exist.

- [ ] Device: launch cold with a hand-written greeting near the 40-character editor limit, let the splash run to handover, and check whether the ring visibly jumps during the crossfade. If it does, the fix is to fold the greeting's line count into the estimate or to reintroduce a cap — deliberately, not by nudging the constant.
